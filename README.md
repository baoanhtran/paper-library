# Research Library Pipeline

INFO-H420 Assignment 3 (ULB): a scheduled Apache Airflow DAG that turns research PDFs in a Google Drive folder into a searchable static web page, with metadata generated by a locally served LLM. The plan, the roles and the interface contract are in [ROADMAP.md](ROADMAP.md).

## Overview and architecture

```text
Google Drive (synced)               Demo machine (WSL2)
ResearchLibrary/papers/*.pdf  ───►  Airflow DAG "paper_pipeline", every 5 minutes
                                      ensure_db               create the SQLite table if needed
                                      find_new_pdfs           PDFs whose filename is not in SQLite yet
                                      process_paper [×N]      one copy per new PDF:
                                        convert_pdf             PyMuPDF4LLM → Markdown
                                        ask_llm                 Ollama (qwen2.5:7b) → JSON metadata
                                        save_metadata           SQLite, data/papers.db
                                      render_html             rebuild index.html from the database
                                      notify_discord [×N]     one webhook message per new paper
ResearchLibrary/output/index.html ◄─┘
```

- **Orchestration:** Apache Airflow 3.3 in standalone mode, one DAG in [dags/paper_pipeline.py](dags/paper_pipeline.py). Helper modules live in [dags/paper_lib/](dags/paper_lib/).
- **PDF to Markdown:** PyMuPDF4LLM. **Metadata:** a local model served by Ollama, called through its OpenAI-compatible API with the `openai` package in JSON mode.
- **Storage and outputs:** one SQLite file on the local machine, outside the synced folder; one static `index.html` in Google Drive; one Discord webhook message per new paper.
- **DAG design:** the per-paper chain is a mapped task group, so one broken paper does not stop the others. The run ends early when there is nothing new, the page is rebuilt even if a paper failed, and only one run is active at a time.

## Setup (WSL2, Airflow, Google Drive)

Prerequisites: Linux, macOS, or Windows 11 with WSL2 (Airflow does not run natively on Windows), Python 3.12, git. Tested on Ubuntu 24.04 in WSL2.

1. Clone the repo into the Linux file system (not under `/mnt/c`, which is much slower):

   ```bash
   git clone https://github.com/baoanhtran/paper-library.git ~/paper-library
   cd ~/paper-library
   ```

2. Create a virtualenv with Airflow and the project libraries. The constraints file pins Airflow's own dependencies:

   ```bash
   python3 -m venv ~/venvs/airflow
   source ~/venvs/airflow/bin/activate
   pip install "apache-airflow==3.3.2" -r requirements.txt \
     --constraint "https://raw.githubusercontent.com/apache/airflow/constraints-3.3.2/constraints-3.12.txt"
   ```

3. Point Airflow at this repo. Airflow keeps its own files in `AIRFLOW_HOME` (default `~/airflow`):

   ```bash
   airflow config get-value core dags_folder   # first run creates ~/airflow/airflow.cfg
   sed -i -E "s|^dags_folder = .*|dags_folder = $HOME/paper-library/dags|; s|^load_examples = .*|load_examples = False|" ~/airflow/airflow.cfg
   airflow db migrate
   ```

   Exporting `AIRFLOW__CORE__DAGS_FOLDER` and `AIRFLOW__CORE__LOAD_EXAMPLES=False` before starting Airflow works too.

4. Google Drive for Desktop (Windows side): install it, sign in, and choose *Mirror files* under Preferences → My Drive. In My Drive, create `ResearchLibrary/papers` and `ResearchLibrary/output`. WSL2 sees them under `/mnt/c/Users/<you>/My Drive/ResearchLibrary/` (check the exact folder in Drive's settings). With *Stream files* instead, make `ResearchLibrary` available offline and mount the drive: `sudo mkdir -p /mnt/g && sudo mount -t drvfs G: /mnt/g`. On macOS the folder is under `~/Library/CloudStorage/GoogleDrive-<account>/My Drive/`.

5. Copy `.env.example` to `.env` and fill in your values (see Configuration). Quote paths that contain spaces, such as `"My Drive"`.

6. Set up the local LLM (see LLM setup) and the Discord webhook (see Discord webhook).

## LLM setup

Role B can develop and test these modules on native Windows, Linux or macOS with Python 3.11+; Airflow is only needed on A's demo machine. From the repository root, create a virtual environment and install the existing dependencies:

```bash
python -m venv .venv
# Linux / macOS / WSL2:
source .venv/bin/activate
# Windows PowerShell instead:
# .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

**Ollama.** Install the [Windows or macOS application](https://ollama.com/download), or install inside Linux/WSL2 with `curl -fsSL https://ollama.com/install.sh | sh` ([Linux instructions](https://docs.ollama.com/linux)). On the demo machine, install inside WSL2 so the endpoint is reachable from Airflow at `localhost`. Start the application/service; if it is not running, use `ollama serve` in another terminal. Then download the configured model:

```bash
ollama pull qwen2.5:7b
ollama list
```

Copy `.env.example` to `.env` if needed, keeping these settings for Ollama:

```dotenv
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:7b
```

`qwen2.5:7b` is the shared demo default and was not part of B's laptop comparison. For the tested RTX 3050 Laptop GPU (4 GB), B recommends **Qwen 2.5 3B Instruct Q4_K_M**: it captured the papers' main contributions more reliably than 1.5B in the three-paper evaluation, at about 0.92 seconds more per call in later repetitions. See the [measured comparison and quality notes](docs/role-b-evaluation.md). With Ollama, pull `qwen2.5:3b` and change `LLM_MODEL` to try the smaller model; the measured Q4_K_M comparison itself used LM Studio.

Downloaded weights take disk space. The first request can include model loading if the model is not already loaded. Use `ollama ps` to inspect the loaded model and CPU/GPU use. The client points at the configured local endpoint and supplies a dummy API key; no cloud API key is required. Ollama documents its [OpenAI-compatible endpoint and JSON mode](https://docs.ollama.com/api/openai-compatibility).

The module sends at most the first 8,000 Markdown characters, with temperature 0.1 and `response_format={"type": "json_object"}`. Configure enough server context for this prefix plus the prompt and response; the character limit is not a token limit. Ollama's [context documentation](https://docs.ollama.com/context-length) explains `OLLAMA_CONTEXT_LENGTH`; restart the server after changing it. An 8,192-token context is a practical starting point for ordinary English papers, subject to available memory.

Keep the exact category list and output-field requirements in the prompt. Wrong field types, including a comma-separated `keywords` string, trigger one further attempt; two invalid responses raise `ValueError`. A server that explicitly rejects `json_object` with HTTP 400 and requires `json_schema` is retried using the same four-field JSON schema. That compatibility request does not consume the invalid-output retry; at most three HTTP requests are made when a format rejection is followed by two invalid answers. Other connection and HTTP failures propagate to the caller for Airflow's task retry.

**Try a real PDF without Airflow.** With the local model server running, put a text-based paper at `data/papers/sample.pdf` and run the [one-paper CLI](docs/scripts/process_paper.py) from the repository root:

```bash
python docs/scripts/process_paper.py data/papers/sample.pdf --output data/metadata/sample.json
```

The command converts the PDF, extracts validated metadata, prints the JSON and saves it at `--output`. It reads the existing configuration module and `.env`; `--base-url`, `--model` and `--markdown-dir` override those settings. On Windows, use `.\.venv\Scripts\python.exe` in place of `python` if the environment is not activated. Run `python docs/scripts/process_paper.py --help` for the options.

The returned JSON has exactly `title`, `summary`, `keywords` (a list of strings) and `category`. Conversion preserves extractable PDF text and supported layout features; it does not perform OCR. Scanned, password-protected, broken or almost textless PDFs raise clear errors. Formulas and complex tables still need visual checking against the source. Local PDFs, converted Markdown and settings stay under the existing ignore rules.

**LM Studio alternative.** Install [LM Studio](https://lmstudio.ai/download), download and load an instruction-tuned model that fits your machine, then start its local server in the Developer tab (or `lms server start`). Use the exact model identifier shown by the server's `/v1/models` endpoint:

```dotenv
LLM_BASE_URL=http://localhost:1234/v1
LLM_MODEL=<loaded-model-identifier>
```

Prefer an instruction model that returns a direct answer, as the roadmap recommends. A reasoning model can exhaust the output budget before completing its JSON. The helper does not send a `reasoning_effort` parameter; any reasoning-off configuration must actually apply to API requests, rather than being assumed from an interactive chat setting.

The same Python modules and tests are used for both backends. Some LM Studio versions require `json_schema` rather than `json_object`; this was observed on the development laptop. The client switches to its four-field schema only for the explicit HTTP 400 response-format rejection. The selected model/backend must support that schema; unrelated HTTP errors still propagate. See [LM Studio's OpenAI compatibility](https://lmstudio.ai/docs/developer/openai-compat) and [structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output) documentation.

Run B's tests without starting an LLM server:

```bash
python -m pytest tests/test_pdf_to_md.py tests/test_llm_metadata.py tests/test_contract.py -q
```

B's [evaluation](docs/role-b-evaluation.md) covers three real PDFs and 18 helper calls: both models returned valid metadata in 9/9 runs each. Mean time across all calls was 10.86 seconds for 3B and 9.21 seconds for 1.5B; later rounds averaged 8.16 and 7.24 seconds. Models were preloaded, so these values exclude model loading. [Portable results](docs/examples/model-comparison.json) and [two actual 3B outputs](docs/examples/qwen3b-real-metadata.json) preserve the evidence. Run `docs/scripts/benchmark_llm.py --help` to repeat the comparison. Check summary claims against the source; valid JSON and exact titles do not establish factual accuracy, and the three-paper result is not a general model ranking.

## Discord webhook

The pipeline posts one message per new paper to a Discord channel (title, summary, category, keywords, file name).

1. In Discord, open the channel's settings → **Integrations** → **Webhooks** → **New Webhook**, name it, and choose **Copy Webhook URL**.
2. Put the URL in `.env` (never in a file that is committed):

   ```dotenv
   DISCORD_WEBHOOK_URL="https://discord.com/api/webhooks/<id>/<token>"
   ```

3. Send a test message without running the pipeline:

   ```bash
   python -c "
   import sys; sys.path.insert(0, 'dags')
   from paper_lib import config
   from paper_lib.notify import notify_new_paper
   notify_new_paper(config.DISCORD_WEBHOOK_URL, {'filename': 'test.pdf', 'title': 'Webhook test',
       'summary': 'Hello from the pipeline.', 'keywords': ['test'], 'category': 'Other'})
   print('sent')"
   ```

The URL is a secret: anyone who has it can post to the channel. If it leaks, delete the webhook in Discord and create a new one. If 'DISCORD_WEBHOOK_URL' is empty, 'notify_discord' is skipped and says so in its log. An HTTP error (for example 404 for a deleted webhook) fails only that task; the database and the page are still correct. A paper that failed earlier in the pipeline is not announced.


## Configuration

All settings are environment variables, read by `dags/paper_lib/config.py`. Copy `.env.example` to `.env` at the repository root and edit it. Relative paths are resolved from the repository root. Quote paths that contain spaces, such as `"My Drive"`.

| Variable | Default | Meaning |
|---|---|---|
| `PAPERS_DIR` | `data/papers` | Folder scanned for PDFs; the Google Drive `ResearchLibrary/papers` folder |
| `OUTPUT_HTML` | `data/output/index.html` | **File** path of the generated page (must end in `index.html`); the Drive `ResearchLibrary/output` folder |
| `DB_PATH` | `data/papers.db` | SQLite database; keep it local, outside the synced folder |
| `MARKDOWN_DIR` | `data/markdown` | Cache of the Markdown converted from each PDF |
| `LLM_BASE_URL` | `http://localhost:11434/v1` | OpenAI-compatible endpoint (Ollama; LM Studio uses port 1234) |
| `LLM_MODEL` | `qwen2.5:7b` | Model name, exactly as shown by `ollama list` |
| `DISCORD_WEBHOOK_URL` | `https://discord.com/api/webhooks/<id>/<token>` | Webhook for notifications |

Example for macOS (Google Drive in Mirror mode):

```dotenv
PAPERS_DIR="/Users/<you>/Library/CloudStorage/GoogleDrive-<account>/My Drive/ResearchLibrary/papers"
OUTPUT_HTML="/Users/<you>/Library/CloudStorage/GoogleDrive-<account>/My Drive/ResearchLibrary/output/index.html"
DB_PATH=data/papers.db
MARKDOWN_DIR=data/markdown
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:3b
```
Notes:

- **Variables already set in the shell win over `.env`.** If the settings do not change after you edit `.env`, run `env | grep -E "PAPERS_DIR|OUTPUT_HTML|LLM_|DISCORD"` and `unset` the old ones. There is no need to `source .env`; `config.py` reads the file itself.
- **Check the settings** without running anything:

  ```bash
  python -c "import sys; sys.path.insert(0,'dags'); from paper_lib import config as c; print(c.PAPERS_DIR, c.PAPERS_DIR.is_dir()); print(c.OUTPUT_HTML); print(c.LLM_MODEL, bool(c.DISCORD_WEBHOOK_URL))"
  ```

- `.env` is listed in `.gitignore`. Keep it that way, since it holds the webhook URL.

## Run and test

```bash
source ~/venvs/airflow/bin/activate
airflow standalone
```

- Open http://localhost:8080 (it also works from the Windows browser). The user is `admin`; the password is in `~/airflow/simple_auth_manager_passwords.json.generated`.
- New DAGs start paused: switch `paper_pipeline` on in the UI, or run `airflow dags unpause paper_pipeline`.
- Drop a PDF into `ResearchLibrary/papers/`. Within about 5 minutes it is converted, summarised, stored, listed in `ResearchLibrary/output/index.html` and announced on Discord. After a restart, the first LLM call takes longer (about 45 s on the demo machine) because the model is loaded into GPU memory; later calls take a few seconds.
- One run without the scheduler, with every task log in the terminal: `airflow dags test paper_pipeline`.

Tests: run `pytest` from the repo root. Module tests run without Airflow (Python 3.11+): `pip install -r requirements.txt`, then `pytest`. The DAG tests in `tests/test_dag.py` are skipped where Airflow is not installed.

## Outputs

For each new PDF the pipeline produces three results; the Markdown text is only an intermediate file.

**1. SQLite record** (`data/papers.db`, local). One row per paper in the `papers` table:

```sql
CREATE TABLE papers (
    filename     TEXT PRIMARY KEY,      -- PDFs are assumed to have unique names
    title        TEXT NOT NULL,
    summary      TEXT NOT NULL,
    keywords     TEXT NOT NULL,         -- JSON array of strings
    category     TEXT NOT NULL,
    processed_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Saving an existing filename updates the row, so re-running is safe. The database uses WAL mode, so `papers.db-wal` and `papers.db-shm` files appear next to it; that is normal. Inspect it with:

```bash
sqlite3 -header -column data/papers.db "select filename, title, category, keywords from papers;"
```

**2. Static web page** (`ResearchLibrary/output/index.html`, synced through Google Drive). One self-contained file with inline CSS and JS and the data embedded as JSON, so it opens straight from disk with no server. It shows one card per paper and has:

- a **search box**: every typed word must appear in the title, summary, keywords, category or file name (case-insensitive); clicking a keyword chip searches for it;
- a **category filter** built from the categories present in the data, combined with the search.

The page is rebuilt from the whole database after each run and written atomically (temporary file, then rename), so Google Drive never syncs a half-written page.

**3. Discord message.** One embed per new paper: title, short summary, category, keywords, file name. See [Discord webhook](#discord-webhook).

Local, not synced: the database and `data/markdown/<name>.md`.

## Troubleshooting

- **`PAPERS_DIR does not exist or is not a folder`** in `find_new_pdfs`: Google Drive is not running or not synced yet, or the path in `.env` is wrong (quote it; with Stream mode, mount the drive first).
- **`paper_pipeline` is missing from the UI:** check `dags_folder` in `~/airflow/airflow.cfg`, then run `airflow dags list-import-errors`.
- **`ModuleNotFoundError: paper_lib` outside Airflow:** add `dags/` to `PYTHONPATH`. Airflow does this itself for the DAG processor and the tasks; the tests do it in `tests/conftest.py`.
- **Port 8080 is already in use:** an older `airflow standalone` is still running (`pgrep -fa airflow`), or set `AIRFLOW__API__PORT` to another port.
- **LLM calls fail:** check `systemctl status ollama` and `curl http://localhost:11434/api/version`; `ollama ps` shows whether the model runs on the GPU.
- **No Discord message:** `DISCORD_WEBHOOK_URL` is empty; `notify_discord` is then skipped and says so in its log.
- **Everything is slow:** keep the repo and the virtualenv in the Linux file system (`~/`), not under `/mnt/c`.
- **No runs for hours:** the PC went to sleep. Scheduled runs need the machine awake.
- **A new PDF is picked up later than expected:** files modified less than 30 s ago (by the WSL clock) wait for the next run, and the WSL2 clock can lag behind Windows (about 12 s on the demo machine, more after the PC sleeps). Compare `date` in WSL with the Windows clock; `sudo hwclock -s` in WSL, or `wsl --shutdown` from Windows, resyncs it.
